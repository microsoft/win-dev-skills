# Reproducible skill benchmarks

Use this protocol to compare agent setups, especially UWP-to-WinUI migrations.
The unit of measurement is a **fresh migration attempt**, not a chat message,
successful build, or screenshot. A good result preserves the original app's
behavior and UI, and another contributor can reproduce how it was assessed.

This is an evaluation guide, not a benchmark runner or a set of performance
claims. A PR description containing scores without its run artifacts is not
reproducible evidence.

The manual route below uses real Copilot CLI and WinApp CLI entrypoints. Its
artifact layout and result fields are conventions to create yourself, not files
generated by a hidden harness.

## 1. Freeze the experiment before running it

Write a run plan outside the agent's accessible workspace. Give it a run ID and
record these fields:

| Input | Record and hold constant |
|---|---|
| Question | Whole-plugin improvement, incremental migration-skill improvement, or automatic skill discovery? Pick one primary comparison. |
| Source | Repository URL, full commit SHA, sample and language directory, shared dependencies, fixture hashes, and any preparation patch. No moving `main`, PR head, or `latest` references in the final record. |
| Treatment | Full plugin/skill commit SHA, local plugin root, manifest, file hashes, enabled skills/agents/tools, and exact ablation patch. A version string alone is insufficient for unpublished changes. |
| Agent | CLI version, explicit model ID (not `auto`), provider, reasoning effort, context tier, permissions, MCP servers, web access, memory policy, and complete command line. |
| Task | Exact prompt bytes, output location, packaging mode, target framework/architecture, dependency versions, and acceptance checklist. |
| Budget | Wall-clock deadline, AI-credit/token limit where supported, continuation/repair limit, and stopping rule. Use the same limits in every arm. |
| Machine | Windows build, CPU/RAM/architecture, desktop resolution/DPI/theme/language, .NET SDK, Windows SDK/UWP tools, WinApp CLI, Windows App SDK/runtime, templates, NuGet configuration, and sensor/language-pack availability. |
| Schedule | Scenario split, repetitions, saved randomized trial order and seed, concurrency, cache policy, and permitted infrastructure retries. |
| Evaluation | Build/launch/render/behavior/fidelity rubric, critical requirements, unsupported-device rules, evaluator version, and any judge model/prompt. |

Pin `global.json`, package versions, template versions, and lock files where the
projects support them. Archive the resolved dependency graph as well. Normal
development skills may request the latest packages; the benchmark prompt must
instead require the frozen versions. Record any drift as a protocol deviation;
do not quietly compare different toolchains.

A model ID is not an immutable service snapshot. Record UTC dates and any
provider-reported revision; publish this limitation if the provider cannot pin
it. Do not promise bit-for-bit deterministic agent output or invent temperature
or seed flags that the chosen CLI does not expose.

### Define what "baseline" means

For migration work, these are useful but different comparisons:

| Arm | Agent-visible configuration | What the contrast measures |
|---|---|---|
| No repository skills | Stock CLI, no WinUI plugin, no WinUI custom agent or instructions. Keep unavoidable CLI built-ins identical and list them. | Candidate versus an unassisted-by-this-repo agent, not versus a bare language model. |
| Scaffold/workflow-only | A pinned, explicitly enumerated scaffold/workflow setup, with migration guidance absent. Preserve its required helper files. | Added value over scaffolding, only if the candidate differs solely by the migration treatment. |
| Candidate | The same scaffold/workflow setup plus the candidate migration skill and its declared dependencies. | Incremental migration treatment. |

If the candidate instead loads the entire plugin and `winui-dev` orchestrator,
label it a **whole-setup comparison**. Differences in design skills, analyzer,
tools, or agent instructions are confounders for a migration-skill-only claim.
For a precise ablation, derive both bundles from one pinned tree, record their
file-level diff, and keep everything except the intended treatment identical.
Do not edit the user's global plugin installation.

The migration skill need not exist in the released plugin. Obtain the actual
candidate commit, verify its `SKILL.md` name and references, and record them.
Do not substitute the WPF migration skill or assume a pending UWP PR has shipped.

Choose **forced use** or **automatic discovery** in advance. Forced use adds an
arm-specific instruction naming the exact skill; keep the migration task itself
identical and publish that instruction. Automatic discovery uses the same task
prompt in every arm and treats failure to select an available skill as an
outcome. Availability is not evidence that the agent actually read the skill.

## 2. Prepare the dataset and machine

The public [Windows universal samples](https://github.com/microsoft/Windows-universal-samples)
provide source scenarios. One concrete source snapshot is
[`4eb2fcb499c5bc549e918920cfd2b64396a650d9`](https://github.com/microsoft/Windows-universal-samples/tree/4eb2fcb499c5bc549e918920cfd2b64396a650d9/Samples).
It contains `Samples\<name>\cs` for all five examples below. This snapshot is a
starting point, **not** an assertion that it was used by previous benchmark
reports. Preserve the repository's common/shared files, assets, and licenses;
copying just a `.csproj` or XAML page is not an equivalent input.

| Scenario | Example acceptance evidence to specify before migration |
|---|---|
| ApplicationData | Set and retrieve sample values, save and reload data across a real process restart, and verify clean first-launch state. Evaluate unsupported roaming semantics explicitly rather than silently dropping them. |
| BasicInput | Navigate every included page and exercise the prescribed keyboard, pointer, and focus interactions. Separate touch/pen requirements from mouse-only coverage. |
| Compass | Verify sensor readings on supported hardware; separately verify the original no-sensor/disabled-device behavior. A friendly "unsupported" message is not proof that heading updates work. |
| OCR | Pin image bytes, language pack, expected normalized text, and file-picker flow. Test recognition, not just opening the image or showing a button. |
| XamlDeferLoadStrategy | Exercise load/unload triggers, navigation and repeated toggles; check the relevant content appears and behaves correctly, not merely that a shell window opens. |

Inspect and, where feasible, run the original UWP app first. Record reference
screenshots, expected outputs, page inventory, and documented platform differences.
Legacy UWP samples can need Visual Studio's UWP workload and the matching Windows
SDK even when the **WinUI target** builds with `dotnet` alone. Document any source
repair patch and apply it identically before all arms, outside the measured phase.

Five familiar samples are a useful development set, not a generalization claim.
Keep a separate held-out set of apps/pages/API combinations that did not guide
skill edits. Freeze it before testing and do not tune on its failures. Report
development and held-out results separately.

Use a disposable Windows VM snapshot or dedicated test machine/account, with an
interactive, unlocked desktop. Do not run UI trials concurrently on one desktop:
focus, dialogs, package identities, and input events interfere. A disconnected
RDP session or headless CI worker may compile successfully but cannot establish
rendering or interaction success.

Provision prerequisites **before** timing trials using the
[setup guidance](plugins/winui/agent-plugin/skills/winui-setup/SKILL.md).
WinApp CLI must support project-mode `run` (the plugin requires 0.6+), and .NET
must support the chosen target framework. Check rather than upgrade during a run:

```powershell
git --version
copilot --version
copilot --help
copilot help environment
copilot help limits
dotnet --info
dotnet --list-sdks
winapp --version
winapp run --help
winapp ui --help
```

Save these outputs with the environment record. Resolve missing prerequisites
and Developer Mode approvals before freezing the image; do not modify a shared
machine's policy, certificates, or installed SDKs to rescue one arm.

Authenticate Copilot in the dedicated environment using `copilot login`, or
inject a supported credential through your secret manager. Copilot CLI documents
`COPILOT_GITHUB_TOKEN`, `GH_TOKEN`, and `GITHUB_TOKEN` in that precedence order.
Do not assume `gh auth status` proves Copilot/model access. Never record tokens,
credential-store contents, or a wholesale environment-variable dump.

Record relevant **non-secret** settings or redacted presence: `COPILOT_HOME`,
`COPILOT_CUSTOM_INSTRUCTIONS_DIRS`, provider/model overrides, proxy configuration,
NuGet cache location, and `WINAPP_DBGTOOLS_DIR` when using crash diagnostics.
Disable auto-update for the experiment. Use the same pre-warmed cache snapshot
for each trial, or consistently measure cold caches; never clear shared caches.

## 3. Isolate each trial, including agent context

Restore the frozen image/state for every scenario-arm-repeat combination. Give
each trial a fresh source copy, empty output directory, new Copilot process and
session, and private configuration/state directory. Do not use `--resume`,
`--continue`, an existing IDE conversation, or previous generated solutions.
Preserve input filenames and paths consistently across arms where practical.

`COPILOT_HOME` isolates CLI state; **it is not a sandbox or a complete skill
discovery boundary**. Audit project and parent directories, user-level
`.copilot`/`.agents`/`.claude` configuration, custom instruction directories,
plugins, hooks, extensions, agents, MCP servers, and organization policy.
`--no-custom-instructions` does not mean "disable every skill."
`--disable-builtin-mcps` does not disable separately configured MCP servers.
Use a clean profile/image instead of deleting or disabling the developer's setup.

Mount only the current arm's bundle and source into the trial environment.
Do not expose other arms' bundles, evaluator answers, benchmark reports, prior
session memory, or earlier trial outputs. Merely placing them in a sibling
directory is not adequate isolation from an agent allowed to run shell commands.

Before spending the full budget, check discovery in a **separate preflight
session**, then discard that session's state:

```powershell
# In the dedicated benchmark environment, outside the win-dev-skills checkout.
$env:COPILOT_HOME = 'C:\bench\preflight\copilot-home'
$env:COPILOT_AUTO_UPDATE = 'false'
copilot --no-auto-update --no-custom-instructions plugin list
copilot --no-auto-update --no-custom-instructions skill list --json

# Candidate/ablation arms only: point at the prepared, pinned plugin root.
$PluginRoot = 'C:\bench-inputs\treatment\agent-plugin'
copilot --no-auto-update --plugin-dir $PluginRoot plugin list
```

Current portable bundles have `plugin.json` and `skills\` under
`plugins\winui\agent-plugin`; older commits may use another layout. Archive the
manifest and verify the selected root. With Copilot CLI 1.0.83, `plugin list`
recognized an external `--plugin-dir` bundle, while `skill list --json` did not
enumerate that bundle's skills. Do not mistake that inventory alone for runtime
activation. A bounded no-tools preflight can check the runtime skill names:

```powershell
copilot --no-auto-update --no-custom-instructions --no-remote-export `
  --disable-builtin-mcps --plugin-dir $PluginRoot `
  --model gpt-5.4-mini --reasoning-effort low --context default `
  --max-ai-credits 30 --available-tools= `
  -p 'Do not call tools or change files. Return only the exact names of skills available in your instructions.'
```

Use your chosen, available model/settings consistently in the real experiment;
the model above is only a discovery example. Repeat preflight without
`--plugin-dir` for the no-repository-skills arm. Require the expected inventory
and inspect the real trial transcript for skill invocations or reads of the
intended `SKILL.md` and references. A model's self-report alone is not proof of
skill execution. Stop on contamination or unresolved discovery differences.

## 4. Run the frozen task

Start with a small, disposable smoke scenario to prove the plumbing. Then run
the full predeclared schedule without modifying the prompt after seeing one arm.
For an initial pilot, at least three independent attempts per scenario and arm
is more informative than one; choose a larger sample based on pilot variability
and the effect worth detecting. Save the actual order, not just the random seed.
Block by scenario/repeat and randomize arm order within each block. Keep desktop
concurrency at one.

A task prompt should identify the source sample, all included pages, the WinUI
target and packaging mode, frozen dependencies, behavior/fidelity requirements,
output location, and budget. For example, replace the bracketed fields and save
the resulting exact text as `task.txt`:

```text
Migrate Samples\[scenario]\cs from the supplied UWP source to a WinUI 3
[target framework, architecture, packaging mode] app in output\[scenario].
Preserve every included page, navigation flow, user-visible behavior and
specified visual structure. Use the supplied dependency versions and fixtures;
do not upgrade tools/packages or fetch a previous migration/benchmark answer.
Build and launch the app, verify meaningful rendered content, and exercise
[the published acceptance interactions]. Report unsupported capabilities and
remaining failures explicitly. Do not remove features, replace behavior with
placeholders, change packaging mode, or relax assertions to obtain a pass.
Use at most [repair limit] repair cycles within [wall-clock budget].
```

The following is a **single-trial invocation template**, not an automated runner.
Run it from a fresh `pwsh -NoProfile` process in the disposable environment.
Prepare the pinned source in `work`, create `artifacts`, and supply `task.txt`
before executing it. Set the model and budget once in the run plan:

```powershell
$TrialRoot = 'C:\bench\run001\ApplicationData\candidate\r01'
$Workspace = Join-Path $TrialRoot 'work'
$Artifacts = Join-Path $TrialRoot 'artifacts'
$env:COPILOT_HOME = Join-Path $TrialRoot 'copilot-home'
$env:COPILOT_AUTO_UPDATE = 'false'
$Model = 'gpt-5.4-mini'
$PluginArgs = @('--plugin-dir', 'C:\bench-inputs\treatment\agent-plugin')
# For no repository skills, use $PluginArgs = @() instead.
# For other arms, mount only that arm's recorded bundle at the same input path.
$Prompt = Get-Content (Join-Path $TrialRoot 'task.txt') -Raw
Set-Location $Workspace

$Started = [DateTimeOffset]::UtcNow
copilot @PluginArgs --model $Model --reasoning-effort low --context default `
  --no-auto-update --no-custom-instructions --disable-builtin-mcps `
  --no-remote-export --no-ask-user --allow-all-tools `
  --max-ai-credits 120 --output-format json `
  --log-dir (Join-Path $Artifacts 'logs') `
  --usage-output-file (Join-Path $Artifacts 'usage.json') `
  --share="$(Join-Path $Artifacts 'session.md')" `
  -p $Prompt 1> (Join-Path $Artifacts 'agent.jsonl') `
  2> (Join-Path $Artifacts 'agent.stderr.txt')
$AgentExit = $LASTEXITCODE
[ordered]@{
    startedUtc = $Started.ToString('o')
    endedUtc = [DateTimeOffset]::UtcNow.ToString('o')
    agentExitCode = $AgentExit
} | ConvertTo-Json | Set-Content (Join-Path $Artifacts 'attempt.json')
```

`--allow-all-tools` permits autonomous shell execution: use it only inside the
disposable, access-controlled environment, never as a security boundary on your
workstation. Freeze permitted network access and secrets exposure as well.
Do not add `--agent winui-dev` to only one arm unless the orchestrator is part of
the treatment. Keep memory disabled (the default in prompt mode); do not enable
it or carry forward its state.

CLI 1.0.83 requires a minimum `--max-ai-credits` value of 30; it is a **soft**
accounting limit, not a hard spending or wall-clock cap. The example's 120 is a
budget choice, not a recommendation inferred from benchmark results. Enforce the
recorded wall-clock deadline independently with a supervisor/operator that tracks
this run's process IDs. Keep partial logs and mark timeouts; do not extend a
failing arm's budget. An instruction to stop is not enforcement.

Save the generated source, untracked assets, patch, and resolved project/package
files when the attempt ends. Preserve failures and missing output files. A zero
agent exit code, confident final answer, or self-generated "PASS" file is not an
application verdict.

## 5. Evaluate the frozen output independently

Do not let the evaluator repair the app or show its answers to the migration
agent. Use the same evaluator tooling for all arms, even if the agent used a
different build helper. Evaluate from a copy of the final source without stale
`bin`/`obj` output; keep build/restore logs, exit codes and deployment evidence.
Freeze and record any evaluator preparation, including automation selectors.
Do not treat the migration skill's own validator `PASS` as ground truth: confirm
that the expected project and mapped source files exist, the build tool actually
ran, and launch succeeded. A missing tool, skipped check, absent project, or
uninspected nonzero exit cannot establish success.

For current WinApp CLI, project-mode launch is:

```powershell
winapp run .\output\ApplicationData\ApplicationData.csproj -c Release --arch x64 --detach --json
```

Use the actual generated project path and frozen configuration. This command
builds and launches; capture its output/exit code, distinguish build failures
from deployment failures, and record the returned app PID. Do not count a failed
launch as a build failure if the logs show compilation succeeded.
The current [workflow skill](plugins/winui/agent-plugin/skills/winui-dev-workflow/SKILL.md)
and [WinApp command source](https://github.com/microsoft/winappcli/blob/67f0884a1577f046896b95d6199a1905f12328f3/src/winapp-CLI/WinApp.Cli/Commands/RunCommand.cs)
describe this entrypoint. Do not use it with an older folder-only `winapp run`.
There is no `winapp build` step in this protocol. `--no-launch` can separate
build/deployment from launch when supported, but still registers the package:
it is not a side-effect-free compilation check.
For crash diagnostics use an attached `--debug-output` run separately; do not
combine it with `--detach` or `--json`.

Then target **that PID**, not a process name or whichever window is focused.
Set `$Artifacts` to the trial's existing evidence directory from the invocation
above (also when evaluating in a separate shell):

```powershell
$AppPid = 12345 # Replace with this trial's recorded launch PID, never $PID.
winapp ui list-windows -a $AppPid --json
winapp ui inspect -a $AppPid --json
winapp ui screenshot -a $AppPid -o (Join-Path $Artifacts 'initial.png')
winapp ui invoke 'RecordedButtonAutomationId' -a $AppPid
winapp ui wait-for 'RecordedResultAutomationId' -a $AppPid --value 'Expected result' -t 5000
winapp ui screenshot -a $AppPid -o (Join-Path $Artifacts 'after-interaction.png')
```

The IDs and expected value are scenario-specific placeholders, not assertions
that these samples already expose those IDs. Save each command's stdout, stderr,
and exit code immediately; a later screenshot must not overwrite an earlier
assertion failure. For multiple windows, record the HWND and use `-w` to scope
the target. The [UI testing skill](plugins/winui/agent-plugin/skills/winui-ui-testing/SKILL.md)
describes interactions; freeze your evaluator script and expected assertions
before the measured trials. Human evaluation is acceptable when documented.

Report these dimensions separately:

| Dimension | Required evidence |
|---|---|
| Build | Clean compilation of the actual migrated app in the required configuration, with build logs and an exit code. |
| Launch | Correct package/executable starts and survives a predeclared observation interval; record identity, PID, window and crash/deployment logs. |
| Render | Meaningful content on every required page, not a blank shell, splash screen, hidden window, or hard-coded screenshot. Inspect screenshots as well as UIA. |
| Behavior | Predeclared interactions and outputs pass, including navigation, persistence across restart, error paths and device-dependent behavior. |
| Fidelity | Side-by-side reference comparison at fixed size/DPI/theme: retained features, layout hierarchy, labels, assets, bindings and accessibility. Document intentional platform adaptations. |

Record `pass`, `fail`, `not_run`, or `unsupported` per assertion, with reason and
artifact path. A compile failure leaves later stages `not_run`, not passed.
Missing hardware identified in preflight is `unsupported` for the hardware
assertion in **every arm**; score the required no-device behavior separately.
An agent disabling a control, deleting a feature, stubbing OCR output, or
suppressing an exception is a failure, not an environmental exemption.

Define overall success as passing all required, supported assertions and all
mandatory stages. State the device coverage alongside it: success without a
compass sensor is not success at compass readings. Preserve all scheduled trials
in the report, including unavailable, timed-out, and interrupted ones. For
infrastructure failures, retain the original attempt and apply the same
predeclared replacement rule to every arm; ordinary agent failures get no
selective reruns.

Prefer objective checks over a single 0-100 score. If using a weighted score,
publish weights, anchors, treatment of failures/missingness, and raw component
scores in advance. Do not compare scores from different rubrics. Blind subjective
reviewers to arm identity; for model judging, pin its prompt/model/settings,
retain its evidence/reasoning, and spot-check against human judgments.

## 6. Retain artifacts and report uncertainty

Keep artifacts outside the plugin checkout and out of future agent contexts.
An example layout (created by the operator, not automatically by this repo):

```text
run001\
  plan.json
  environment.txt
  schedule.csv
  prompts\
  treatment-manifests\
  reference-evidence\
  trials\<scenario>\<arm>\<repeat>\
    command.txt
    agent.jsonl
    agent.stderr.txt
    session.md
    usage.json
    attempt.json
    logs\
    source-final\
    build.log
    launch.json
    ui-results.json
    screenshots\
    verdict.json
  summary.csv
```

One summary row should identify run/scenario/arm/repeat and source/treatment
SHAs; status for each stage; supported assertions passed/total and unsupported
count; overall verdict; elapsed and active agent time; evaluator time; input,
output, cache and reasoning tokens where available; reported credits/cost; retry
count; and relative evidence paths. Use `null` for unavailable telemetry, not
zero. Archive raw `usage.json` because client/provider accounting can change.
Distinguish AI credits or premium requests from currency; any currency estimate
needs the pricing source/date. Include failed attempts and evaluation costs,
and separate setup/download time from measured migration time.

Publish scenario-level paired results, raw counts and denominators, not only an
average or "100%." Show each repeat, spread (for example median and range/IQR),
and uncertainty for the paired difference. If estimating a confidence interval,
state the method and account for trials clustered within scenarios (for example,
a paired scenario-level bootstrap). Three repeats on one sample are not three
independent applications. With few scenarios, treat estimates as exploratory;
do not turn an unstable interval or a small score difference into a superiority
claim. Do not omit failures from time/cost or score summaries.

A report/PR should include the frozen question and contrast, all refs/settings,
dataset split and coverage, actual schedule and deviations, rubric, per-trial
results, aggregate uncertainty, artifact link with checksums/retention policy,
and exact reproduction steps. Distinguish what you measured from assumptions
and historical claims. Redact prompts, local paths, logs and screenshots as
needed before sharing; never publish auth state, tokens, signing keys, private
source, or raw credential-bearing configuration. Explain redactions that limit
reproduction.

## 7. Clean up only what the run owns

Prefer reverting the disposable image. Otherwise keep an ownership ledger of
created directories, package full names, certificates (if any), and process IDs
with their executable paths/start times. Stop only those processes, checking
that a PID was not reused; never kill all `dotnet`, `copilot`, or similarly named
processes. Unregister only the recorded benchmark packages and remove only the
recorded run-owned files after evidence is retained. Never wildcard-delete app
data, uninstall the developer's plugins, clear global caches, or change machine
policy during cleanup.

## What was exercised for this guide

The documentation smoke check used Windows, PowerShell 7.6.6 and Copilot CLI
